# 新聞事件持續追蹤系統 — 測試策略

測試分級採用 [Google 的 test size 分類](https://testing.googleblog.com/2010/12/test-sizes.html)：依「允許怎麼跑」而非「概念上測什麼」分類。

- **Small**：單一程序，無網路、無 sleep/timer、無真實檔案系統或外部 I/O。毫秒級、完全確定性。small 測試若會 flaky，那一定是測試本身的 bug。
- **Medium**：單機多程序，允許 localhost 網路（例如真實的本地資料庫）。較慢，有固有的非確定性。
- **Large**：可存取任何東西——其他機器、真實外部服務。是驗證真實端到端行為的唯一方式，但慢且信號最不可靠。

---

## 一、最重要的區分：測試 vs 評估

系統的核心行為由 LLM 產生（抽取、歸屬、因果、敘事），輸出非確定性。這裡有兩件**性質完全不同**的事常被混為一談：

| | 軟體測試 | 模型品質評估 |
|---|---|---|
| 問題 | 給定固定的 LLM 輸出，系統行為是否正確？ | LLM 的輸出本身好不好？ |
| 方法 | 在 `LLMProvider` 注入固定回應 | 對人工標註測試集跑指標 |
| 性質 | 確定性、二元通過／失敗 | 統計性、有門檻 |
| 速度 | 毫秒 | 分鐘到小時，且花 API 費用 |
| 執行時機 | 每次修改（CI） | 階段關卡前、換模型前、改 prompt 後 |
| 失敗意義 | 程式有 bug | 模型／prompt 不夠好 |

**把評估放進 CI 會毀掉測試套件的可信度**——它會間歇性失敗，而失敗原因是模型抖動而非程式錯誤，久了就沒人理會紅燈。兩者必須分開，用不同的執行方式與不同的心理預期。

## 二、讓系統可測試的三道接縫

測試策略的品質取決於架構是否留了接縫。以下三處必須在對應任務**實作時就做出來**，事後補會非常痛：

### 接縫 1：`LLMProvider`（ADR-0002 已定）

所有 LLM 呼叫走此介面。測試時注入固定回應，使「歸屬判定」「因果生成」「事件標題生成」等原本非確定性的行為全部變成 small 測試。

這是 ADR-0002 的隱藏價值：抽象層的第一個受益者不是「換供應商」，而是「能寫測試」。

### 接縫 2：抓取層（`Fetcher`）

爬蟲不可在測試中觸及真實網站。做法：

- 從真實站台**錄製** RSS XML 與 HTML 快照，存為 fixture
- 解析邏輯（`sites.py` 移植而來）對 fixture 執行，全部 small 測試
- **fixture 只能偵測「你改壞了解析程式」，偵測不到「網站改版了」**

網站改版必須靠**生產環境的來源健康度監測**（任務 11）發現，那是監測而非測試。兩者機制不同、時機不同，缺一不可。這個區分很重要：許多專案誤以為爬蟲測試能防網站改版，結果兩邊都沒防到。

### 接縫 3：時鐘（`Clock`）

`active → dormant → 喚醒`、分頻排程、24h/48h SLA 全都與時間有關。所有時間讀取走注入的 clock，禁止直接呼叫 `timezone.now()`。

有了這道接縫，「事件靜置 30 日後轉為 dormant」「dormant 事件的官方源檢查頻率不降低」都是 small 測試，不需要真的等 30 天，也不需要 `sleep`。

## 三、金字塔形狀的誠實預期

理想是 80% small / 15% medium / 5% large。本專案會**比這個扁**，原因是明確的：

- pgvector、CHECK constraint、FTS generated column、遞迴 CTE **在 SQLite 上都不存在**，因此所有涉及資料庫的測試必須跑真實 PostgreSQL → 依定義屬 medium
- 這不是設計缺陷，是採用資料庫原生能力（ADR-0001、0003、0004）的必然代價，且該代價換到的是「護欄無法被繞過」

**緩解方式是把純邏輯擠出資料庫**。以下都是純函式，必須是 small 測試，且它們涵蓋了大部分高風險邏輯：

- 中文 bigram 切分
- SimHash 計算與相似度判定
- 案號／統編／標案編號的正規化與比對
- `Event` 狀態機的轉換規則
- 風險分級判定（含自然人 × 審級是否確定）
- 措辭檢查器的規則層
- 日期解析（移植自 `common.py` 的 `parse_date`）

預期形狀約 **60% small / 35% medium / 5% large**。

## 四、TDD 的適用範圍

適合紅綠重構的部分——行為明確、輸出可預期、邊界條件多：

| 對象 | 為何適合 |
|------|---------|
| 措辭檢查器規則層 | 「這句話違規／不違規」是明確的二元判斷，邊界案例多，正是 TDD 的主場 |
| 識別碼正規化 | 案號格式變體多（全形半形、有無「年度」、空白差異），逐個補測試最有效率 |
| `Event` 狀態機 | 合法與非法轉換可完整列舉 |
| 風險分級判定 | 判定條件已明確定義 |
| SimHash 與 bigram | 輸入輸出關係清楚 |
| 遞迴 CTE 的深度上限與環偵測 | 「含環的圖不應無限遞迴」是先寫得出來的測試 |

**不適合 TDD**，應在形狀穩定後才補測試：

- HDBSCAN 參數調校（探索性，正確答案未知）
- Prompt 設計（迭代式，靠評估而非測試）
- SEO 與版面（無明確斷言對象）
- Scope 0 的驗證性 spike（本來就是為了找出答案）

## 五、各 Scope 的測試計畫

### Test plan: Scope 1 — 文件入庫

**Small**
- RSS/HTML 解析：各來源的 fixture → 正確抽出標題、日期、內文、URL。含畸形輸入（缺日期、空內文、編碼異常）
- `parse_date` 對各種日期格式的解析（移植既有實作，順帶補齊測試）
- SimHash 計算與相似度門檻判定
- URL 正規化（去除追蹤參數後同一文章應得同一 canonical URL）

**Medium**（需真實 PostgreSQL）
- `Document` upsert 冪等性：同一 URL 寫入兩次不產生重複列、不拋例外
- `content_class` 預設值與約束
- `Source` 連續失敗計數與自動降頻的狀態變化
- Celery 任務在 `acks_late` 下被中斷後重跑，結果一致（冪等性的實際驗證，ADR-0007 的核心約束）

**Large**（不進 CI，手動或排程執行）
- 對真實站台的來源健康檢查：每個 adapter 實際抓一篇，驗證選擇器仍有效。失敗時告警而非讓 CI 變紅——這是監測，不是測試

## 六、評估（Evaluation）而非測試

以人工標註測試集（任務 20）為基礎，跑指標並比對門檻。以腳本執行、產出報告，**不進 CI**。

### 執行時機

階段關卡前、更換模型前後、prompt 有實質修改後。

### 指標與門檻——以及兩個必須避開的陷阱

| 指標 | 門檻 | 說明 |
|------|------|------|
| Hybrid 召回率@k | 待基準建立後定 | ADR-0005 明訂**召回率優先於準確率**：召回不到的事件，LLM 再準也判不出來 |
| 歸屬誤判率 | <5%（M4） | ⚠️ **見下方陷阱 1** |
| 歸屬涵蓋率 | 與誤判率**成對**檢視 | 陷阱 1 的解藥 |
| 措辭違規攔截率 | ≥95%（M6） | ⚠️ **見下方陷阱 2** |
| 措辭誤攔率 | 與攔截率**成對**檢視 | 陷阱 2 的解藥 |
| L1 抽取欄位準確率 | 待基準建立後定 | 同時服務 ADR-0002 的本地模型比較（本地須達 API 的 95%） |

**陷阱 1：M4 可以靠什麼都不歸屬來達成。** 一個永遠回答「不屬於任何事件」的系統，誤歸屬率是 0%，完美達標，但系統毫無用處。**誤判率必須與涵蓋率成對呈現**，單獨看誤判率的驗收是無效驗收。

**陷阱 2：M6 可以靠全部攔截來達成。** 一個攔截所有內容的檢查器，違規攔截率是 100%，但系統永遠發不出任何東西。**攔截率必須與誤攔率成對呈現**，否則調校時會被指標引導到錯誤方向。

規格中的 M4 與 M6 應據此補上配對指標，否則兩個 release blocker 都是可以被滿足卻無意義的。

### 標註測試集的三重用途

任務 20 的標註集會被以下三處共用，因此值得投入時間認真製作：

1. Scope 2 的召回率量測（任務 19）
2. Scope 3 的歸屬準確率驗收（M4）
3. ADR-0002 的本地模型與 API 品質比較

措辭檢查器另需**獨立的標註集**（違規／不違規句子），因為它的標註對象是句子而非文件關聯，無法共用。

## 量測揭露的四個缺陷（任務 19，2026-08-30）

召回率量測的價值不在於得到一個數字，而在於**數字錯得離譜時，逼出的
四個缺陷是任何單元測試都測不到的**。初次量測 11.4%，最終 91.3%，
中間四次修正沒有一次是憑感覺調參數：

| # | 缺陷 | 量測給的線索 | 修正 |
|---|------|------------|------|
| 1 | 關鍵字通道依 `published_at` 排序 | 京華城 30 篇正例全漏，MRR 0 | 改依 `ts_rank` |
| 2 | `core_terms` 缺事件的身分詞 | 漏掉的正例標題全含「京華城」 | 加入標題去後綴的詞 |
| 3 | `per_channel=100` 截斷太早 | 正例全在命中集合內，名次 1–440 | 提高到 500 |
| 4 | 身分詞與涉案人併成一個詞袋 | 加詞反而降低召回率（11/30 → 4/30） | 拆成兩個通道 |

**第 4 點是唯一無法從單元測試發現的。** 前三點理論上寫得夠仔細的測試
可以擋下，但「加詞會讓結果變差」違反直覺到不會有人為它寫測試——
`ts_rank` 沒有 IDF，每個 bigram 等重，九個人名的 bigram 數量壓過一個
建物名。這是 PostgreSQL FTS 的性質，不是程式的 bug，只有拿真實語料
量測才會撞到。

第 3 點的錯誤根源是**把兩個不同用途的參數當成同一個**：`per_channel`
控制融合看得到多少候選（索引掃描，便宜），`top_k` 控制送進 LLM 的量
（昂貴）。為了省 LLM 成本而縮小 `per_channel`，省不到錢，只是讓召回
率掉了 44 個百分點。

### 量測反過來挑戰標註

大巨蛋案召回率 0%，唯一的正例排在第 335 名——查下去發現那是
G-DRAGON 演唱會的黃牛票新聞，標註錯了（見 fixtures/LABELING_GUIDE.md
的修正紀錄）。**檢索系統與標註者不同意時，不必然是檢索錯了。**

驗收指標的可信度也因此要分開看：
