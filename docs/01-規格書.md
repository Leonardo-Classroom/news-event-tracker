# 新聞事件持續追蹤系統 — 技術規格書

- 狀態：草稿 v1
- 日期：2026-08-29
- 規格層級：Full spec（新系統、跨多資料源、有法律風險、預估數月工期）

---

## 1. 背景與問題

台灣的重大司法案件與政商弊案，在公共視野中的生命週期與它們在司法/行政程序中的實際生命週期嚴重脫節。

新聞媒體對一個案件的報導密度呈現雙峰分布：**事件爆發時**與**判決宣判時**。兩個高峰之間往往相隔三到八年，期間幾乎零報導。但案件本身在這段期間持續推進——起訴、一審辯論、宣判、上訴、二審、更審、確定、執行。這些進展都有官方紀錄，只是沒有人把它轉譯回大眾語言。

具體造成三個問題：

1. **民眾無從得知案件現況。** 搜尋一個案件名稱，得到的是數年前的舊聞，沒有任何頁面回答「所以後來呢」。
2. **官方資料公開但不可用。** 司法院裁判書、立法院議案、監察院糾正案、政府決標公告都是公開資料，但格式零散、術語艱澀、彼此不互相關聯，且與新聞報導之間沒有任何連結。
3. **沒有服務把兩者串起來。** 現有新聞聚合器（含 Google News）以「文章」為單位，不以「事件」為單位；它們回答「今天有什麼新聞」，不回答「這個案子進行到哪」。

**為什麼是現在：** 兩個前提條件在近年才同時成立——司法院已提供正式的裁判書開放 API（異動清單 + 全文），立法院有開放資料平台；同時 LLM 的結構化抽取成本已降到可以對每日數千篇文件做全量處理的程度（尤其是具備 context caching 的推論服務）。這兩者任一不成立，本系統都不可行。

## 2. 目標

以可驗證的結果陳述，非實作陳述：

| ID | 目標 |
|----|------|
| G1 | 任何人以案件的常見稱呼搜尋，能找到該事件頁；頁面首屏即顯示「目前進度」與「最後更新日期」 |
| G2 | 事件頁呈現單一條時間線，每個節點含日期、事實敘述、可點擊的原始出處；出處同時涵蓋新聞與官方文件 |
| G3 | 系統在無人干預下持續納入新進展：新聞發布後 24 小時內、裁判書公開後 48 小時內，歸入對應事件 |
| G4 | 事件不因新聞停止報導而停止追蹤；沉寂事件在官方資料出現新進展時自動喚醒並通知訂閱者 |
| G5 | 因果關係呈現時，明確區分「報導明述的因果」與「系統推論的因果」，且每一條都可回溯到原始出處 |
| G6 | 所有涉及尚未判決確定之個人的敘述，措辭符合無罪推定原則 |
| G7 | 公開頁面不呈現任何第三方新聞全文；僅呈現系統自製的敘述與原文連結 |

## 3. 非目標

明確排除，以防範範圍蔓延：

- **不做新聞閱讀器或即時新聞牆。** 不與新聞 App 競爭「今天有什麼新聞」。系統的單位是事件，不是文章。
- **不做觀點、評論或立場分析。** 系統不對案件是非、政治責任、判決妥適性做任何評價。
- **不做全庫語意問答。** 這不是「新聞版 ChatGPT」；不提供對整個語料庫的開放式提問。
- **不追蹤台灣司法/行政管轄以外的事件**（第一版）。國際新聞不納入。
- **不做秒級即時性。** 批次排程（小時級到日級）即可滿足所有目標。
- **不自動發布。** 任何事件進入公開狀態前必經人工審核，無例外。
- **不提供原文轉載或鏡像存檔服務。** 原始新聞全文僅作內部分析語料，永不對外呈現。
- **不做行動原生 App。** 響應式網頁即可。
- **不做使用者生成內容**（留言、投稿、共筆）第一版不開放。

## 4. 提案設計

### 4.1 分層架構

```
L0  採集層   RSS/sitemap 輪詢（主力） + Playwright 爬蟲（fallback） + 官方 API adapter
             → URL 去重 + SimHash 近似去重（同一則通稿被多家轉載）
L1  抽取層   LLM 結構化抽取：日期、人物、機構、公司、案號、法院、審級、罪名、標案編號、事件觸發詞
             → 版本化保存（記錄 model 與 prompt version）
L2  召回層   Hybrid Retrieval：pgvector 向量檢索 + PostgreSQL 全文檢索（BM25 類）
             → 給定事件，撈出候選新文件
L3  事件層   Event Linking（候選 → LLM 判定歸屬 → 寫入 EventDocument）
             Event Detection（未歸屬文件叢集 → 過門檻 → 產生事件候選）
             Per-Event 時序知識子圖（節點=人/組織/案件/標案；邊=因果、時序）
L4  敘事層   時間線生成、因果鏈說明、事件回顧摘要、進度變更偵測與通知
L5  應用層   Django（伺服器端渲染）+ 審核後台 + Celery Beat 排程
```

**關鍵設計決策：不建全庫知識圖譜。** 全庫只維持 hybrid 向量+全文檢索，僅被系統認定為「事件」的內容才建立知識子圖。追蹤中的事件量級是數十到數百，每個數十到數百份文件；這個規模建圖的成本可忽略，品質也遠高於全庫粗糙抽取。詳見 §5 替代方案。

### 4.2 核心資料模型

```
Source          來源註冊。type: news_rss | news_scrape | judicial_api | ly_api | cy_scrape | pcc_dataset
                欄位：輪詢頻率、robots 政策、認證設定、服務時段、最後成功時間、連續失敗數

Document        統一的原始文件（新聞、裁判書、議案、糾正案、決標公告皆為此型）
                欄位：source, external_id, url, published_at, fetched_at, title,
                      raw_body [internal_only], simhash, canonical_of (轉載歸併指向)

Extraction      對 Document 的結構化抽取結果。版本化，一份 Document 可有多版
                欄位：document, schema_kind (judicial | corruption | generic),
                      payload (JSONB), model, prompt_version, created_at

Entity          人、組織、公司、法院、機關、標案、案號
EntityAlias     別名（本名/綽號/舊稱/案件俗稱）— 同時服務檢索與 SEO

Event           事件本體
                status:      candidate → draft → active → dormant → closed
                visibility:  private | public
                欄位：slug (SEO)、title、summary、current_status_text、
                      last_progress_at、next_key_date、domain (judicial|corruption|generic)

EventDocument   事件 ↔ 文件（多對多）
                欄位：relevance_score、判定理由、判定者 (auto|human)、判定時間

TimelineNode    時間線節點
                欄位：event、occurred_on、node_type (起訴|開庭|宣判|上訴|確定|糾正|決標|報導)、
                      fact_text (系統自製)、citations (指向 Document + 段落位置)

CausalEdge      因果邊
                欄位：from_node、to_node、kind (stated | inferred)、confidence、
                      evidence (stated 必填：Document + 引文區間)

EventMergeLog   事件合併/分裂紀錄，保留完整歷史與可回溯性
ReviewTask      人工審核佇列
Subscription    訂閱（事件 ↔ 訂閱者）
GenerationLog   所有 LLM 生成文字的版本紀錄（model、prompt version、輸入摘要）
```

### 4.3 事件自動偵測

每日批次，順序不可調換：

1. 取近 N 日新增 Document 的 embedding
2. **先對現有 active/dormant 事件做歸屬**：hybrid 召回 top-k 事件 → LLM 判定是否屬於 → 寫入 `EventDocument`
3. 剩餘未歸屬文件做叢集
4. 叢集通過門檻才升為事件候選。**門檻明訂為：≥3 家不同媒體 且 ≥5 篇文件 且 跨 ≥2 天**（防止單一媒體的專題稿或轉載鏈被誤判為重大事件）
5. LLM 生成事件標題、摘要、初始時間線 → 狀態設為 `draft`
6. 進入 `ReviewTask` 佇列，人工審核通過後才 `active` + `public`

步驟 2 必須先於步驟 3，否則既有事件的後續報導會被叢集成新事件，造成大量重複。

### 4.3.1 風險分級審核

人工審核以**形式確認**為主要模式（審核者為單人，量能有限），因此安全性由自動閘門承擔，並依**法律風險**（非事件重要性）分流：

| 風險等級 | 判定條件 | 審核方式 |
|---------|---------|---------|
| 高 | 事件涉及**具名自然人**且案件**尚未判決確定** | 必須逐條確認時間線與措辭，禁止批次通過 |
| 中 | 涉及法人／機關，或個人案件已判決確定 | 形式確認（標題 + 摘要）即可 |
| 低 | 政策、天災、無指名對象之事件 | 形式確認，允許批次通過 |

風險等級由 `Extraction` 的實體結果**自動判定**（是否含自然人 × 案件審級是否確定），不由人工指定，避免誤判為低風險而略過。

配套的硬性閘門——這些是「形式確認」在中低風險上得以成立的前提：

- **措辭檢查器為 blocking gate**：未通過者不得進入 `draft`，且不提供人工繞過選項
- **公開文字保守化**：對外敘述僅允許程序事實句型（「檢方於 X 日就 Y 罪嫌起訴 Z」），不得出現行為斷定
- **`inferred` 因果邊預設不公開**，須人工逐條勾選才顯示
- **更正／下架申訴管道**，處理 SLA 24 小時；下架即時生效、事後補審

### 4.4 生命週期與排程頻率

| 狀態 | 進入條件 | 新聞源檢查 | 官方源檢查 |
|------|---------|-----------|-----------|
| `active` | 審核通過 | 每日 | 每日 |
| `dormant` | 連續 30 日無新增 TimelineNode | 每週 | **維持每日** |
| `closed` | 人工標記（判決確定且無後續程序） | 停止 | 每季一次（防翻案/再審） |

**dormant 狀態下官方源檢查頻率刻意不降低。** 這是整個系統價值的所在——新聞沉寂期正是判決出爐的時期。降低官方源頻率等於放棄核心功能。

### 4.5 因果與敘事的護欄

這是系統最容易產生「看似合理、實則捏造」內容的環節，因此設計為強制約束而非提示詞建議：

- `CausalEdge.kind = stated` **必須**附帶 Document 引用與引文區間（資料庫層 constraint），指向報導中明確陳述該因果的文字
- `CausalEdge.kind = inferred` **必須**有 confidence 值，且在 UI 中呈現於獨立區塊，不得與 stated 混排於同一段敘述
- `TimelineNode.fact_text` 僅記錄可查證事實（誰、何時、做了什麼），推論不進時間線
- **措辭檢查器**：所有生成文字產出後執行檢查（規則比對 + 小模型判定），攔截將未判決確定之個人描述為已定罪的表述；未通過者不得進入 draft
- 所有生成文字寫入 `GenerationLog`，保留 model 與 prompt version，可完整回溯

### 4.6 公開／內部內容分離

法律硬約束，落實在 schema 層而非流程層：

- `Document.raw_body` 標記為 internal-only，序列化白名單機制確保永不出現在任何對外 response
- 公開頁面組成：系統自製摘要、時間線（自製敘述文字）、實體關係、來源清單（標題 + 媒體 + 日期 + 原文連結）
- 引文限度：僅 `stated` 因果邊可引用短句作為證據，需明確標示出處，且有長度上限
- 以自動化測試強制驗證：任何公開端點的回應不得包含**新聞類** Document 的 `raw_body` 內容

**裁判書等公文可全文呈現。** 依著作權法第 9 條，憲法、法律、命令或公文不得為著作權之標的，裁判書屬公文，故無授權問題。這使官方源成為系統唯一能完整展示的一手內容，是相對於新聞源的實質優勢。但仍受兩項限制：

- 依法不公開或應遮蔽之案件類型（性侵害、少年事件、部分家事事件）不得納入
- 司法院公開版裁判書的去識別化程度不一，納入前須執行個資遮蔽檢查

因此 `Document` 需增加 `content_class` 欄位：`copyrighted`（新聞，內部限定）與 `public_record`（公文，可公開）。序列化白名單依此欄位決定，而非一律封鎖全文。

### 4.7 SEO 作為一級需求

系統的核心目標是「讓大家想起來」，而大眾想起某案件時的實際行為是搜尋案件關鍵字。**因此事件頁的搜尋能見度是本產品觸及使用者的主要管道，不是次要優化項。** 這決定了幾個架構選擇：

- **伺服器端渲染**（Django template 直出），不採用前端 SPA
- URL 設計：`/event/<slug>/`，slug 穩定不變（事件更名時保留舊 slug 301）
- `EntityAlias` 表提供案件俗稱，餵給頁面 title、meta description 與內文
- schema.org 結構化資料標記（`NewsArticle` / `Event` / `Dataset`）
- 動態生成 `sitemap.xml`，含 `lastmod`（對應 `last_progress_at`）
- 每個事件頁 `<title>` 包含：案件俗稱 + 當事人 + 「進度／後續」等搜尋意圖詞

### 4.8 技術堆疊

| 層 | 選擇 | 理由 |
|----|------|------|
| Web | Django 5（SSR）| SEO 需求；ORM 與 admin 適合審核後台 |
| DB | PostgreSQL 16 + pgvector | 單一資料庫同時滿足關聯、全文檢索、向量檢索，避免多套儲存 |
| 任務 | Celery + Redis | 排程、重試、逾時控制；取代既有爬蟲的自製看門狗 |
| 爬蟲 | RSS/sitemap 為主，Playwright 為輔 | 成本差一到兩個數量級 |
| Embedding | 地端 BGE-M3 或 Qwen3-Embedding | 中文檢索表現佳、零 API 成本、資料不外流 |
| LLM | DeepSeek API，分級用模型 | context caching 對「事件檔案為穩定前綴」的場景結構性契合 |
| 環境 | conda `leo3.10` | 沿用既有環境 |

**LLM 使用分級：** L1 大量結構化抽取用便宜檔；L3 事件歸屬判定用中檔；L4 因果推理與敘事生成用旗艦檔。業務程式碼一律透過 provider 抽象層呼叫，不得直接依賴 DeepSeek SDK。

### 4.9 既有爬蟲資產的處置

繼承自 `news report/crawler/`：

| 既有元件 | 處置 |
|---------|------|
| `common.py` 反偵測 context、Cloudflare 等待、`sanitize`、`parse_date` | 直接繼承，抽為 `crawler/core` |
| `sites.py` 各站解析邏輯 | 繼承，改為 adapter 插件註冊制 |
| `crawl_robust.py` 多程序、續爬、看門狗 | 設計思路保留，改由 Celery 的 soft/hard timeout 與 retry 實現 |
| `_state/*.json` 檔案式狀態 | **淘汰**。多 worker 下有競爭條件，改 PostgreSQL |
| `dataset/**/*.txt` 檔案儲存 | **淘汰**。改 DB（需檢索、去重、關聯） |
| 全程 Playwright 的抓取策略 | **改變**。主力改 RSS/sitemap 輪詢，Playwright 僅用於無 feed 或有 Cloudflare 的站 |

### 4.10 分期上線

| 階段 | 內容 | 產出的可驗證能力 |
|------|------|-----------------|
| P0 | Django 骨架、資料模型、新聞 RSS pipeline、去重 | 新聞持續入庫，可查詢 |
| P1 | L1 抽取、L2 召回、事件偵測、時間線生成 | 能自動產生事件 draft |
| P2 | 司法院裁判書 API 接入 | 判決進度能接回事件（**核心價值驗證點**）|
| P3 | 公開網站、SEO、審核後台 | 對外可用 |
| P4 | 立法院 API、政府採購網、監察院 | 弊案類事件的完整鏈路 |
| P5 | 訂閱通知、事件回顧卡、休眠喚醒推播 | 「讓大家想起來」的主動端 |

官方源的排序依據：司法院（價值最高、有正式 API）→ 立法院（有 API）→ 採購網（有資料集下載）→ 監察院（純爬蟲、最不穩定）。

## 5. 替代方案評估

**A. 全庫 GraphRAG（Microsoft GraphRAG 式）**
對整個新聞語料建立實體圖與 community summary。
*否決理由：* 大語料的索引成本被報導達到數萬美元等級；更關鍵的是新聞是高頻 append-only 資料流，community detection 需要全域重算，無法增量更新。本系統每天新增數千份文件，此方案在營運上不可行。

**B. 純向量 RAG 問答**
建一個大向量庫，使用者提問時檢索並生成答案。
*否決理由：* 沒有事件本體，就無法表達「狀態」與「持續追蹤」。系統無從知道某事件是否仍在進行、上次進展是何時、是否該喚醒。這會產出一個新聞搜尋引擎，而非事件追蹤器——直接違背 G3、G4。

**C. 人工策展**
由編輯人工建立與維護事件檔案（如維基百科模式）。
*否決理由：* 不可規模化，且與「大家會忘記」的問題同構——人也會忘記去更新。但此方案的審核環節被保留並整合進 §4.3 步驟 6，作為自動化的品質閘門。

**D. 使用現成新聞事件 API（GDELT 等）**
*否決理由：* 台灣繁中新聞覆蓋率低，且完全沒有台灣官方司法/行政資料。本系統的差異化正是官方源，此方案取代不了。

**E. 維持現狀（do nothing baseline）**
使用者以 Google 搜尋 + 維基百科查詢案件現況。
*否決理由：* 這正是問題陳述描述的現況。維基百科僅涵蓋極少數最知名案件且更新滯後；Google 搜尋結果以新聞近因排序，查不到沉寂期的官方進展。

## 6. 風險與待決問題

### 風險

| ID | 風險 | 緩解 |
|----|------|------|
| R1 | **法律：誹謗。** 公開具名個人的未定案司法敘述 | 人工審核閘門（無例外）、無罪推定措辭檢查器、僅陳述可查證程序事實 |
| R2 | **法律：著作權。** 新聞報導受著作權保護 | 公開頁不呈現全文（schema 層強制 + 自動化測試）、僅自製敘述 + 原文連結 |
| R3 | **LLM 捏造因果** | stated 邊強制引用（DB constraint）、inferred 邊獨立呈現、生成全程版本化可稽核 |
| R4 | **自動叢集品質差**，產生重複或汙染的事件 | merge/split 機制 + `EventMergeLog` + 審核閘門 + 明訂偵測門檻 |
| R5 | **爬蟲被封或網站改版** | RSS 優先降低壓力、adapter 隔離爆炸半徑、來源健康度監測與告警 |
| R6 | **司法院 API 限制**：服務時段 00:00–06:00、Token 6 小時效期 | 排程須配合時段；Token 自動更新；抓取失敗需可續 |
| R7 | **LLM 成本失控** | 分級用模型、context caching、重運算僅施加於 active 事件 |
| R8 | **人工審核為形式確認**，無法擔任品質防線 | 安全性移至自動閘門：風險分級（§4.3.1）、措辭檢查器為 blocking gate、保守化句型、inferred 因果預設不公開 |
| R9 | **個資。** 公開彙整個人的司法紀錄，即使各筆皆為公開資料，彙整本身可能產生新的侵害 | 限定於具公共利益之重大案件；提供當事人申訴管道；不納入輕微案件 |
| R11 | **新聞與裁判書缺乏共同識別碼。** 實測 238,339 篇新聞中僅 0.06% 含案號，且多為憲判字。裁判書雖必有案號，卻無法據此接回新聞事件——而那正是核心價值所在 | 改採組合訊號橋接：當事人姓名（37%）+ 法院（10.3%）+ 時間鄰近 + 語意相似度。須於 Scope 0 任務 2 取得裁判書實例後實證驗證 |
| R10 | **自架主機可用性。** WSL2 主機非為長期對外服務設計：停電、重啟、WSL 未自動啟動、動態 IP 皆會導致斷線 | Cloudflare Tunnel 對外（免固定 IP）；服務以 systemd 管理並設 `Restart=always`；WSL 啟用 systemd 以支援開機自啟；外部 uptime 監測告警 |

### 已解決的決策

| ID | 問題 | 結論 |
|----|------|------|
| Q1 | 審核量能 | **形式確認為主。** 因此改採風險分級審核（§4.3.1），安全性由自動閘門承擔 |
| Q2 | 訂閱機制 | **兩者都做：** Email 訂閱（double opt-in，免註冊）+ 完整帳號系統。P3 工期需含 auth |
| Q3 | 部署環境 | **本機自架對外**（RTX 4090 / 32 核 / 62GB）。地端 embedding 免費且資料不外流；風險見 R10 |
| Q4 | 對外 API | **第一版提供。** 公開/內部邊界須依 `content_class` 設計，並加限流 |
| Q5 | 裁判書全文 | **可全文呈現。** 屬公文，著作權法第 9 條不得為著作權標的；限制見 §4.6 |
