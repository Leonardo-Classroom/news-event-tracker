# 5. 事件偵測採用「先歸屬、後叢集」兩階段流程，叢集使用 HDBSCAN

## Status

Accepted

## Context

系統需在無人指定的情況下自動發現新事件，同時將新文件持續歸入既有的追蹤事件。這兩件事常被混為一談，但性質截然不同：

- **歸屬**：目標事件已知（active 與 dormant 事件，數十到數百個），問題是「這篇文件屬於哪一個，或都不屬於」
- **偵測**：目標事件未知，問題是「這批未歸屬文件中，哪些構成一個值得追蹤的新事件」

事件會**持續成長**：一個追蹤中的案件在數年間會累積數百篇文件。若每日對全部文件重新叢集，同一事件在不同日期會被切成不同的簇，且簇與既有事件的對應關係難以維持穩定。

規格已明訂偵測門檻：≥3 家不同媒體 且 ≥5 篇文件 且 跨 ≥2 天。門檻的目的是排除單一媒體的專題稿與轉載鏈。

量體：每日新增約 3000 篇。經歸屬階段後，未歸屬文件預估為數百篇量級。

### 選項比較

| 選項 | 優點 | 缺點 | 風險 |
|------|------|------|------|
| 每日對全部近期文件跑 HDBSCAN 批次 | 實作單純 | 不 incremental；既有事件的後續報導會被叢集成新簇，需再做簇↔事件對應 | **大量重複事件**。簇的邊界每日變動，事件身分不穩定 |
| Online / incremental clustering（leader clustering、串流質心） | 天然支援增量與事件成長 | 質心會隨事件演變而漂移；長事件的早期與晚期文件可能不再相似 | 對「事件歷時數年」的場景，單一質心無法代表整個事件 |
| 純 LLM 判定（每篇文件問屬於哪個事件） | 準確率最高 | 對 3000 篇 × 數百事件是組合爆炸 | 成本不可行 |
| **兩階段：先歸屬（hybrid 召回 + LLM 判定），未歸屬者跑 HDBSCAN** | 歸屬階段成本可控（召回 top-k 後才用 LLM）；偵測階段資料量小；事件身分穩定 | 兩套機制需分別調校 | 歸屬階段漏判會使文件流入偵測階段，產生與既有事件重複的新簇（緩解：合併機制） |

**HDBSCAN 相對其他叢集演算法的關鍵優勢**：它不需預設簇數，且會將無法歸入任何密集區的點標記為 **noise**。這正好對應本系統的需求——「不是每篇新聞都構成事件」。單篇的雜訊報導自然落入 noise，不需額外的過濾規則。K-means 之類必須把每個點指派到某個簇的演算法，會強迫雜訊產生虛假事件。

## Decision

我們將採用**兩階段流程**，順序不可調換：

**階段一 — 歸屬（對既有事件）**

1. 對每份新文件，以 hybrid 檢索（dense 向量 + 關鍵字／識別碼）召回 top-k 個候選事件（k 取 5–10）
2. 對候選事件以 LLM 判定歸屬。因候選數受 k 限制，LLM 呼叫量為 O(文件數)，而非 O(文件數 × 事件數)
3. **識別碼精確比對優先**：若文件的案號／標案編號與某事件的既有識別碼相符，直接歸屬，跳過 LLM

**階段二 — 偵測（對未歸屬文件）**

4. 取近 7 日未歸屬文件的 dense 向量，執行 **HDBSCAN**
5. 被標記為 noise 的文件不產生事件，但保留於資料庫，下次批次仍納入（一則報導可能數日後才發展成事件）
6. 通過門檻（≥3 家媒體、≥5 篇、跨 ≥2 天）的簇升為事件候選
7. LLM 生成標題、摘要、初始時間線 → `draft` → 進入審核佇列

**階段一必須先於階段二。** 否則既有事件的後續報導會進入叢集，產生與既有事件重複的新事件。

**配套的合併／分裂機制**：`EventMergeLog` 記錄所有合併與分裂操作並保留可回溯性。合併時 `EventDocument` 關聯轉移，舊事件的 slug 保留並 301 導向新事件（SEO 要求）。

## 實測修正（2026-08-30）：識別碼路徑無法橋接新聞與裁判書

任務 15 對 238,339 篇語料以規則抽取識別碼後，本 ADR「識別碼精確比對優先」
的前提被實測推翻——**新聞幾乎不寫案號**：

| 文件類型 | 有案號的比例 |
|---------|------------|
| 新聞 | **0.06%**（143 篇） |
| 裁判書（Scope 5） | 預期 100% |

而且那 143 篇的案號**幾乎全是「憲判字」**——憲法法庭判決本身即為新聞，
才會被引用字號。一般刑事、民事案件的案號（金重訴字、上訴字、易字）
在新聞中幾乎不出現。

（已確認非正則過嚴：寬鬆樣式命中 169 篇，差額 26 篇全為公文文號
如「台內地字第1080123651號」，正確排除。）

**這對核心價值命題構成直接風險。** 識別碼路徑能完美處理
裁判書↔裁判書的關聯，卻**無法把裁判書接回新聞事件**——而
「新聞停了、判決還在，把判決接回讀者記得的那個事件」正是本系統存在的理由。

**替代橋接訊號的實測覆蓋率（新聞端）：**

| 訊號 | 覆蓋率 |
|------|--------|
| 法院名稱 | 10.29% |
| 檢察機關 | 3.60% |
| 刑度 | 1.13% |
| 具名當事人（標註集中屬於事件者，標題） | 37% |

沒有任何單一訊號足以獨立橋接。可行的方式是**組合訊號**：
當事人姓名 + 法院／檢察機關 + 時間鄰近 + 語意相似度。

**因此本 ADR 階段一步驟 3 需擴充**：原文僅有「識別碼精確比對優先」，
應改為分層——

1. 識別碼精確比對（裁判書之間、少數引用字號的新聞）
2. **具名當事人 + 機關 + 時間窗**（新聞↔裁判書的主要橋接）
3. 向量語意相似度（前兩者皆無時）

### 穿刺驗證的結果（Scope 0 任務 2，2026-08-30）

以司法院**公開查詢介面**（不需 API 帳號）取得真實裁判書
「臺灣臺北地方法院113年度金訴字第51號」（柯文哲京華城案，115.03.26 宣判，
全文約 30 萬字），對照標註集中該事件的 30 篇新聞實測。

**先是一次錯誤的測試方向。** 以裁判書的訊號回頭搜尋新聞：

| 橋接方式 | 全庫命中 | 涵蓋標註集 | 精確度 |
|---------|---------|-----------|--------|
| 案號精確比對 | 5 | **1/30** | — |
| 被告姓名（任一） | 2,547 | 20/30 | 0.8% |
| 姓名(≥2) + 法院 + ±90 天 | 221 | 15/30 | 6.8% |

看似不可行。但**這個測試方向本身是錯的**——ADR-0005 的流程不是
「用裁判書去撈新聞」，而是**事件已存在**（帶著從新聞累積的實體集合），
裁判書到來時比對**既有的事件檔案**。

**正確方向的結果：**

事件核心詞在裁判書中的出現次數：

    京華城 786   柯文哲 1,185   容積 1,058   沈慶京 334   應曉薇 407

九個核心詞裁判書涵蓋八個。把裁判書當成待歸屬文件時：

    京華城容積案   特徵詞 3 個，命中 3   ← 最相符
    新竹棒球場案   特徵詞 4 個，命中 1
    其餘四事件     命中 0

**乾淨地歸入正確事件。停損條件未觸發，可以繼續。**

**根本原因是一種不對稱性，應納入設計：**

| | 實體密度 | 涵蓋範圍 |
|---|---------|---------|
| 裁判書 | 高——列出全部當事人、日期、案由、金額 | 整個案件 |
| 新聞 | 低——每篇只涵蓋一個時點 | 案件的片段 |

因此兩個方向的難度不同：**裁判書 → 事件容易**（裁判書包含事件的整套詞彙）；
**新聞 → 事件較難**（每篇只有片段）。歸屬邏輯應區別對待，
不可假設兩者對稱。

**這也解釋了先前的失敗**：以裁判書的少數欄位（案號、被告姓名）去搜尋新聞，
等於用整體的一小部分去比對片段；而以事件的整體詞彙去比對裁判書，
則是用片段的集合去比對整體——後者才是資訊量匹配的方向。

## Consequences

**變得更容易：**

- 事件身分穩定：事件一旦建立即有固定識別，不會因每日重新叢集而變動。這是時間線得以持續累積的前提
- LLM 成本可控：歸屬階段的呼叫量與事件總數無關
- 雜訊處理：HDBSCAN 的 noise 標記免去撰寫啟發式過濾規則
- 偵測階段資料量小（數百篇），HDBSCAN 的計算成本可忽略

**變得更困難：**

- 兩套機制需分別調校：歸屬的 top-k 與 LLM 判定 prompt、偵測的 HDBSCAN 參數（`min_cluster_size`、`min_samples`）與門檻。兩者的失敗模式不同，需分別建立量測
- 歸屬階段的**漏判**會直接導致重複事件——文件沒被歸入既有事件，就會在偵測階段形成新簇。這使合併機制成為必需品而非附加功能
- HDBSCAN 對 1024 維向量的距離度量敏感，可能需先降維（UMAP）才有良好表現。這增加一個需調校的環節

**明確承擔的風險：**

「先歸屬後叢集」的正確性完全依賴歸屬階段的召回率。若 hybrid 檢索的 top-k 沒撈到正確事件，LLM 再準也無從判定。因此**召回率的量測優先於準確率的量測**——這一點需在 P1 的測試設計中明確體現。
