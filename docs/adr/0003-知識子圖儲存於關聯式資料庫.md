# 3. Per-event 知識子圖儲存於 PostgreSQL 關聯表，不引入圖資料庫或 RAG 框架

## Status

Accepted

## Context

規格的核心設計決策是「不建全庫知識圖譜，只有被認定為事件的內容才建子圖」。這使得圖的規模與一般 GraphRAG 情境有數量級的差異：

- 追蹤中的事件數：數十到數百
- 每個事件的節點數：數十到數百（實體 + 時間線節點）
- 每個事件的邊數：同數量級
- **查詢永遠限定在單一事件的子圖內**，不存在跨事件的全域圖遍歷需求

需要的圖操作也很有限：取出某事件的全部節點與邊、依時間排序、找出兩節點間的因果路徑（深度通常 < 5）。

本系統的圖模型有幾項非通用的需求：

- `CausalEdge` 必須區分 `stated`（報導明述，強制附 Document 引用與引文區間）與 `inferred`（系統推論，須有 confidence，且預設不對外呈現）
- 邊的引用需可回溯到具體文件的具體段落
- 所有生成內容需版本化（`GenerationLog`），與圖資料共同構成稽核軌跡
- 圖資料需與 `Event`、`Document`、`ReviewTask` 在同一交易中維持一致（例如：審核通過時同時改變事件狀態與邊的可見性）

### 選項比較

| 選項 | 優點 | 缺點 | 風險 |
|------|------|------|------|
| **PostgreSQL 關聯表**（node / edge 兩表 + 遞迴 CTE） | 零新元件；與其他資料同交易、同備份；完全自訂 schema | 複雜圖演算法（社群偵測、PageRank）寫起來痛苦 | 若未來需要全域圖分析，SQL 會變得難以維護 |
| Neo4j | 圖查詢語言表達力強；圖演算法內建 | 多一個服務；需維護 PG ↔ Neo4j 同步；跨儲存無法保證交易一致性 | 審核狀態與圖可見性分屬兩個儲存，不一致時會導致**不該公開的推論邊被公開**——這是法律風險，不只是資料問題 |
| LightRAG / Graphiti 等 RAG 框架 | 開箱即用的建圖與檢索流程 | 框架的通用實體/關係模型無法表達 stated/inferred 區分與強制引用約束 | **框架會綁架資料模型。** 本系統最重要的護欄（引用強制、推論隔離）正是框架不提供的部分，最終會演變成與框架對抗 |

## Decision

我們將以 **PostgreSQL 關聯表**儲存 per-event 知識子圖，不引入圖資料庫，也不引入 LightRAG / Graphiti / Microsoft GraphRAG 等框架。

Schema 要點：

- `TimelineNode` 與 `Entity` 為節點；`CausalEdge` 與 `EventEntity` 為邊
- `CausalEdge` 以資料庫 **CHECK constraint 強制**：`kind = 'stated'` 時 `evidence_document_id` 與引文區間不得為 NULL
- 多跳查詢以遞迴 CTE 實作，深度上限設為常數（避免環狀因果導致無限遞迴）
- 圖的可見性（`inferred` 邊是否公開）與 `Event.visibility`、`ReviewTask` 同表同交易

## Consequences

**變得更容易：**

- 資料一致性：審核狀態變更與圖可見性變更在同一交易內完成，不存在「事件已下架但推論邊仍公開」的視窗
- 備份與還原：`pg_dump` 涵蓋全部資料，無跨儲存協調問題
- 護欄的強制性：引用必填是資料庫層的 constraint，任何寫入路徑（含未來的批次腳本、修補程式）都無法繞過。若在框架內，這只能是應用層的約定
- 部署：自架 WSL2 主機少一個需要維運的服務

**變得更困難：**

- 若未來需要跨事件的全域圖分析（例如「哪些人物同時出現在多個弊案中」），遞迴 CTE 的表達力與效能都不如 Cypher。**但這類分析目前是 Non-Goal**（規格明確排除全庫語意問答與觀點分析）
- 開發者需自行實作拓撲排序、路徑查找等操作，而非呼叫現成函式庫。考量到圖規模僅數百節點，這些實作可以是最樸素的版本，複雜度可控
- 無法直接套用 GraphRAG 社群的現成檢索策略

**明確放棄的東西：**

放棄了 GraphRAG 框架生態的現成能力，換取對護欄的完全控制。這個交換的前提是「圖很小、查詢很簡單、但正確性要求很高」——如果這個前提改變（例如未來要做全庫圖分析），本 ADR 應被取代。
