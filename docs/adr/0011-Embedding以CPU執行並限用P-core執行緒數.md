# 11. Embedding 以 CPU 執行，執行緒數限為 P-core 數

## Status

Accepted（修訂 [ADR-0004](0004-Embedding採用BGE-M3與HNSW索引.md) 的執行裝置；模型與索引選擇不變）

## Context

ADR-0004 選定 BGE-M3 並假設其在 GPU 上執行，佔用約 2.5GB VRAM。實作階段有兩項變化：

1. **GPU 不可用。** 一個使用者自行啟動的 `llama-server` 於 19.8 天前卡死在 D 狀態，佔用 22,989 MiB / 24,564 MiB VRAM 且無法以任何訊號終止（詳見 ADR-0010）。可用 VRAM 僅約 1.5GB，不足以載入 BGE-M3。
2. **本地 LLM 計畫已取消**（ADR-0009）。ADR-0004 中「2.5GB 不排擠本地 LLM」的論證因此失效——GPU 上已無其他競爭對象，改用 CPU 也不犧牲任何東西。

專案擁有者指定改以 CPU 執行。這同時解除了「必須先重啟 WSL 才能進入 Scope 2」的相依。

**實測結果（i9-14900K，BGE-M3，max_seq_length=512，batch=8）**

| torch 執行緒數 | 篇/秒 | 3 萬篇回填 |
|---------------|-------|-----------|
| 4 | 1.27 | 6.5 小時 |
| 8 | 1.83 | 4.5 小時 |
| **16** | **2.43** | **3.4 小時** |
| 32 | 0.92 | 9.1 小時 |

**關鍵發現：16 執行緒比 32 執行緒快 2.6 倍。**

i9-14900K 是混合架構——8 個 P-core（超執行緒後 16 個邏輯執行緒）加 16 個 E-core。Transformer 推論在每一層都有同步點，整體速度取決於最慢的執行緒。把工作平均分配到 E-core 上，會讓每個同步點都等待慢核心，反而大幅拖累整體。

若未經實測而直接採用 `torch.set_num_threads(os.cpu_count())` 這個常見寫法，會付出 2.6 倍的代價，且不會有任何錯誤徵狀。

另外實測 `batch=16` 慢於 `batch=8`（0.5 vs 0.9 篇/秒，於 32 執行緒下），同樣指向記憶體頻寬與執行緒爭用而非算力不足。

**吞吐是否足夠**（以 ADR-0009 的過濾後語料估算）：

- 日常增量：過濾後約 500 篇/日 → 約 3.4 分鐘。可忽略
- 一次性回填：過濾後 1.3–3.8 萬篇 → 1.5–4.4 小時。單次隔夜作業，可接受

### 選項比較

| 選項 | 優點 | 缺點 | 風險 |
|------|------|------|------|
| **CPU，16 執行緒** | 立即可用，不需等待 GPU 釋出；不與爬蟲搶 GPU；E-core 保留給 Celery worker | 回填需數小時 | 語料規模大幅成長時回填時間線性增加 |
| CPU，32 執行緒（預設寫法） | 無 | **慢 2.6 倍**，且無任何錯誤徵狀 | 沉默的效能損失 |
| GPU | 快數十倍 | **當前不可用**（VRAM 被卡死程序佔滿）；需先重啟 WSL | 進度被一個與專案無關的系統故障阻塞 |
| 雲端 embedding API | 零本機資源 | 每篇付費且語料外流；與地端運算的方向矛盾 | 回填數萬篇的成本與延遲 |

## Decision

1. **Embedding 於 CPU 執行**，由設定值 `EMBEDDING_DEVICE` 控制（預設 `cpu`）。
2. **執行緒數限為 16**，由設定值 `EMBEDDING_THREADS` 控制。**此數值必須隨硬體重新實測，不可假設等於 `os.cpu_count()`。**
3. **`max_seq_length` 設為 1024**。新聞文章多在 800–1500 字，1024 token 足以涵蓋；BGE-M3 預設的 8192 對本語料是浪費。
4. **batch size 設為 8**，實測優於 16。
5. **模型與索引選擇維持 ADR-0004 不變**：BGE-M3、1024 維、`halfvec`、HNSW。本 ADR 只改執行裝置與調校參數。
6. **保留切換回 GPU 的路徑**：`EMBEDDING_DEVICE=cuda` 即可切換，無需改動程式碼。GPU 釋出後可用相同的標註測試集比較品質與吞吐再決定。

## Consequences

**變得更容易：**

- Scope 2 不再相依於 WSL 重啟，可在 GPU 問題解決前推進
- 不與 Playwright 爬蟲競爭 GPU 資源
- E-core 未被 embedding 佔用，仍可服務 Celery worker 與瀏覽器程序——這是限用 P-core 的附帶好處，而非僅是妥協
- 部署不需要 CUDA 環境

**變得更困難：**

- 回填是數小時等級的作業，需以可續跑的批次任務實作（中斷後能從上次進度接續），不能是一次性腳本
- 日後若語料規模大幅成長（例如納入全部 25 萬則新聞而非過濾後的子集），回填時間會線性增加至數十小時，屆時應重新評估 GPU
- 執行緒數是硬體相關的魔術數字。必須在設定中明確標註其來源為實測，否則換機器時會被沿用而失效

**必須記錄的教訓：**

`torch.set_num_threads(os.cpu_count())` 在混合架構 CPU 上是效能陷阱。本專案的任何 CPU 推論工作（未來若有 reranker 或小模型分類器）都應先做同樣的執行緒掃描，不可沿用直覺值。
