# 1. 中文檢索採用 PostgreSQL 內建 FTS（bigram）加結構化識別碼欄位

## Status

Accepted

## Context

系統的 L2 召回層需要 hybrid 檢索（向量 + 關鍵字），用於：給定一個追蹤中的事件，從每日新增文件中撈出候選。

繁體中文沒有詞界，PostgreSQL 內建的 `to_tsvector` 對中文無法正確斷詞（會把整段當成單一 token 或逐字切分）。常見解法是安裝 `zhparser`（基於 SCWS）或 `pg_jieba` extension。

但本系統的檢索需求有一項特殊性質：**司法與弊案領域的關鍵檢索標的大量是精確識別碼**——裁判書案號（如「111年度金重訴字第123號」）、統一編號、標案編號、法院代碼。這類字串：

- 對斷詞器而言是難題（混合數字、中文、專有格式）
- 但對系統而言根本不需要斷詞——它們已經在 L1 抽取階段被結構化抽出，存於 `Extraction.payload`
- 用精確比對（B-tree / GIN on JSONB）遠比任何全文檢索準確

扣掉識別碼之後，剩餘的自然語言關鍵字召回需求，與向量檢索的涵蓋範圍高度重疊。

其他約束：維運人力為一人；部署在自架 WSL2 主機並計畫 Docker 化；規格的 Non-Goals 明確排除「全庫語意問答」，因此不需要高精度的全庫搜尋品質。

### 選項比較

| 選項 | 優點 | 缺點 | 風險 |
|------|------|------|------|
| PG FTS + `zhparser` / `pg_jieba` | 真正的中文斷詞；單一資料庫 | extension 需從原始碼編譯；內建詞典以簡體為主，繁中需自訂詞典 | Docker 化須自建 PostgreSQL image 並維護；升級 PG 版本時需重新處理 extension 相容性 |
| 外掛 Meilisearch | 中文分詞內建（charabia）；單一 binary，部署簡單 | 多一個服務；需維護 PG → Meilisearch 的資料同步 | 同步落後或失敗時，搜尋結果與頁面內容不一致，且不易察覺 |
| 外掛 Elasticsearch | IK 分詞器成熟，中文檢索業界標準 | JVM 記憶體開銷大；運維複雜度高 | 對本系統的資料規模是過度設計，排擠 4090 主機的其他用途 |
| **PG 內建 FTS + bigram 切分 + 結構化識別碼欄位** | 零 extension、零新服務；識別碼查詢準確率最高 | bigram 的自然語言召回準確率低於真斷詞 | 若自然語言召回品質不足以支撐事件歸屬，需更換方案 |
| 純向量、不做關鍵字檢索 | 元件最少 | 對精確識別碼的檢索能力極差 | 直接違反核心需求——案號查不到就無法將裁判書歸入正確事件 |

## Decision

我們將採用 **PostgreSQL 內建 FTS 搭配 bigram 切分**，並將精確識別碼獨立為結構化欄位建索引。

具體做法：

1. **識別碼走結構化欄位。** L1 抽取階段將案號、統一編號、標案編號、法院代碼等寫入 `Extraction.payload` 的固定鍵，並建立 GIN 索引（JSONB）或提升為獨立欄位。事件歸屬時，識別碼精確比對優先於任何模糊檢索。
2. **自然語言部分用 bigram。** 中文文字以 bigram 切分後餵入 `to_tsvector('simple', ...)`，儲存於 generated column 並建 GIN 索引。不安裝任何第三方 extension。
3. **檢索介面隔離。** 所有關鍵字檢索透過單一 `KeywordSearchBackend` 介面呼叫，實作可替換。

## Consequences

**變得更容易：**

- 部署與 Docker 化：可直接使用官方 `postgres` image，無需自建
- 備份與還原：單一資料庫，`pg_dump` 即完整備份，無需協調多個儲存的一致性
- 識別碼檢索：準確率為 100%，優於任何基於斷詞的方案。裁判書歸入正確事件的路徑最短且最可靠
- PostgreSQL 版本升級：無 extension 相容性顧慮

**變得更困難：**

- 自然語言關鍵字的召回品質低於真斷詞方案。bigram 會產生較多雜訊（例如「起訴書」切成「起訴」「訴書」，「訴書」是無意義的 bigram），排序品質下降
- tsvector 體積比真斷詞大（bigram 產生的 token 數約為字數，而非詞數），索引較肥
- 若未來需要面向使用者的全文搜尋功能（目前是 Non-Goal），此方案品質可能不足

**已知的升級路徑：**

若自然語言召回品質經量測不足，依序考慮：(a) 改用 BGE-M3 的 sparse 輸出（learned lexical weights）取代 bigram FTS，這不需新增服務，見 ADR-0004；(b) 才考慮引入 `zhparser`。`KeywordSearchBackend` 介面的存在使兩者皆為局部替換。

**需要驗證的假設：**

「識別碼查詢準確率高 + 向量召回」的組合足以支撐事件歸屬的 <5% 誤歸屬率（規格 M4）。這需在 P1 以實際資料量測；若不成立，本 ADR 應被取代。
